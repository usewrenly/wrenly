Generated applications that store user accounts, notes, or records require an isolated database.
Wrenly provisions a separate PostgreSQL **Development database** per project so generated apps
never share credentials or data with Wrenly's own control database.

## How it works

1. **Describe a stateful application.**  
   In **Auto**, describe what the application should store (for example, an authenticated notes
   application with create, edit, and delete operations). When database storage is required,
   Wrenly pauses and prompts for database approval before provisioning anything.
2. **Create and attach the Development database.**  
   Click **Create database & build** (or **Connect database & build** if the project already
   has a Development database). Wrenly starts an isolated PostgreSQL container for the project
   and builds the application source alongside its schema migrations.
3. **Rehearse and apply migrations.**  
   Once the build succeeds, review the migration summary in the conversation and click
   **Back up, rehearse & apply**. Wrenly tests the migrations against a temporary clone first,
   then applies them to the project's Development database.
4. **Verify in Preview and Browse data.**  
   Open **Preview** to test sign-in and record operations in the running application, then open
   **Database → Browse data** to inspect the persisted rows directly without a SQL console.

```text
Describe app → Create database & build
  → Back up, rehearse & apply migrations
  → Test in Preview → Inspect rows in Database → Browse data
```

## Local setup

If you installed Wrenly with `bunx @wrenly/cli@beta install --previews --databases`, both
PostgreSQL runtime images and `WRENLY_APP_DATABASES_ENABLED=true` are already configured.

When running directly from a source checkout, build the two local runtime images once from the
repository root:

```bash
docker build -t wrenly/postgres-runtime:17 packages/sandbox/images/postgres
docker build -t wrenly/database-socket:1 packages/sandbox/images/database-socket
```

Enable both flags in your root `.env`:

```dotenv
WRENLY_PREVIEW_ENABLED=true
WRENLY_APP_DATABASES_ENABLED=true
```

Restart Wrenly (`bun dev` or `bunx @wrenly/cli@beta start --directory "$HOME/wrenly"`), then
refresh the workspace. A **Database** tab appears beside **Preview**, **Code**, and **Logs**.

> **If the Database tab is missing:** confirm the API startup log reports
> `developmentDatabases: true`. If it reports `false`, update `.env` and restart the API process.

## Operational guidelines

- **Safe page reloads:** If you reload while a database or migration action is running, the
  conversation card reconnects to the persisted job. If a button state appears stale, select
  **Reload card** or **Check saved action** rather than submitting a second request.
- **Stop vs. Delete:** Stop the active preview before stopping its Development database. Stopping
  preserves persisted rows on disk so they remain intact when started again.
- **Iterative edits:** Keep Development selected when modifying views or adding columns. Schema
  changes generate a new migration approval card rather than mutating existing tables silently.
- **Back up `.wrenly/data` and `.env` together:** Wrenly stores local database key material under
  the data directory. Both `.env` and `.wrenly/data` are required to recover existing encrypted
  database credentials.
- **Unix socket isolation:** Generated containers remain network-isolated and connect only over
  an authenticated local Unix socket (`PGHOST`/`PGPORT` for Next.js Drizzle, `DB_HOST`/`DB_PORT`
  for Laravel `pgsql`), never `DATABASE_URL` or hardcoded TCP credentials.

## Troubleshooting

- **Manifest or migration path mismatch (`wrenly.app.json`):** Ask Wrenly in the next turn to
  reconcile `wrenly.app.json` with the existing `database/migrations/` or `drizzle/` files. You
  do not need to delete or recreate the database.
- **Runtime query error in Preview:** Open **Logs** in the workspace pane, copy the error, and
  ask Wrenly to fix the query or validation logic with Development selected.
- **Interrupted rehearsal:** Open **Database → Manage resource** and select **Verify and recover
  a failed rehearsal** (or **Resolve rehearsal**). Wrenly cleans up temporary rehearsal containers,
  checks the primary tables, and restores normal access without dropping data.

## Development vs. Production

`WRENLY_APP_DATABASES_ENABLED=true` enables **Development** databases for interactive workspace
building and previews. **Production** databases remain strictly separate for live published
deployments; see [Production database evaluation](/docs/guides/production-database-evaluation).
