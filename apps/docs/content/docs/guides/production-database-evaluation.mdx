Wrenly keeps **Development** and **Production** app data strictly isolated. Test rows, user
accounts, and migrations created inside a project workspace remain in Development and are never
copied automatically to Production.

- **Development database:** Ephemeral workspace PostgreSQL database attached to sandbox previews.
- **Production database:** Separate TLS-verified PostgreSQL 17 server used exclusively by
  published deployments.

## Single-host evaluation

You do not need multiple servers or cloud infrastructure to evaluate Production databases end to end.
The complete topology runs on one Linux host:

| Component | Role | Single-host location |
| --- | --- | --- |
| **Wrenly control DB** | Stores Wrenly accounts, projects, and build logs | Existing PostgreSQL instance on port `65432` |
| **Production app DB server** | Hosts isolated app databases over TLS | Separate Docker container on port `5434` |
| **Deployment target** | Coolify host running published containers | Local host (`127.0.0.1`) over SSH |
| **Runtime broker & ingress** | Enforces Unix-socket DB access and ingress isolation | Local Docker images built from this repository |

Because `@wrenly/cli` does not run `sudo`, alter system SSH configuration, or provision external
TLS database servers, Production database evaluation is configured explicitly below. Use
disposable test projects while this feature remains **Experimental**.

## Step 1 · Build local runtime images

Complete [Set up publishing](/docs/guides/publishing-setup) (Gitea, local registry on `5001`,
and Coolify) first, then build the required images and `@wrenly/api` from the repository root:

```bash
docker build -t wrenly/postgres-runtime:17 packages/sandbox/images/postgres
docker build -t wrenly/database-socket:1 packages/sandbox/images/database-socket
docker build -t wrenly/database-socket:2 packages/sandbox/images/database-socket
docker build -t wrenly/deployment-ingress:1 packages/sandbox/images/deployment-ingress
bun run --filter @wrenly/api build
```

Upload the trusted broker and ingress images to your local private registry:

```bash
bun run prepare-production-images --confirm-private-upload
```

Copy the three environment variables printed by the command into your root `.env`
(`WRENLY_PRODUCTION_BROKER_IMAGE_ID`, `WRENLY_DEPLOYMENT_INGRESS_IMAGE_ID`, and
`WRENLY_DEPLOYMENT_INGRESS_IMAGE`).

## Step 2 · Install the host runtime helper

Wrenly executes read-only Docker inspection and socket lifecycle operations on the deployment host
through a dedicated helper binary. Install the built bundle into `/usr/local/lib/wrenly`:

```bash
sudo install -d -m 0755 /usr/local/lib/wrenly
sudo install -m 0644 apps/api/dist/runtime-host.js /usr/local/lib/wrenly/runtime-host.js
```

Inspect `command -v bun` and create `/usr/local/bin/wrenly-runtime-host` pointing to your Bun
binary (replace `/home/YOUR_USER/.bun/bin/bun` with the output of `command -v bun`):

```bash
sudo tee /usr/local/bin/wrenly-runtime-host >/dev/null <<'EOF'
#!/bin/sh
exec /home/YOUR_USER/.bun/bin/bun --no-env-file /usr/local/lib/wrenly/runtime-host.js
EOF
sudo chmod 0755 /usr/local/bin/wrenly-runtime-host
sudo chown root:root /usr/local/bin/wrenly-runtime-host /usr/local/lib/wrenly/runtime-host.js
```

> If deploying to a separate remote host instead of `127.0.0.1`, copy `runtime-host.js`, load
> `docker save wrenly/database-socket:2` onto that host, and confirm its `docker image inspect`
> ID matches `WRENLY_PRODUCTION_BROKER_IMAGE_ID`.

## Step 3 · Start an isolated TLS PostgreSQL 17 server

Production app databases require a dedicated PostgreSQL 17 server with TLS enabled (never
Wrenly's control database). For single-host evaluation, start an isolated container on port `5434`
with a self-signed certificate:

```bash
mkdir -p .local/prod-pg/certs
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout .local/prod-pg/certs/server.key \
  -out .local/prod-pg/certs/server.crt \
  -subj "/CN=127.0.0.1" \
  -addext "subjectAltName=IP:127.0.0.1,DNS:localhost"
chmod 600 .local/prod-pg/certs/server.key
chmod 644 .local/prod-pg/certs/server.crt

docker run -d --name wrenly-eval-app-pg \
  --restart unless-stopped \
  -p 127.0.0.1:5434:5432 \
  -e POSTGRES_USER=wrenly_admin \
  -e POSTGRES_PASSWORD=EVAL_ADMIN_PASS_CHANGE_ME \
  -e POSTGRES_DB=postgres \
  -v "$PWD/.local/prod-pg/certs:/certs:ro" \
  postgres:17 \
  -c ssl=on \
  -c ssl_cert_file=/certs/server.crt \
  -c ssl_key_file=/certs/server.key
```

> If you already run a separate private PostgreSQL 17 instance with TLS, skip Step 3 and supply
> its host, port, admin credentials, and CA certificate in Step 5. Never target Wrenly's own
> control database.

## Step 4 · Enable flags in `.env`

Add these flags to your root `.env` and restart Wrenly (`bun dev` or `@wrenly/cli start`):

```dotenv
WRENLY_PREVIEW_ENABLED=true
WRENLY_APP_DATABASES_ENABLED=true
WRENLY_PUBLISHING_ENABLED=true
WRENLY_PRODUCTION_DATABASES_ENABLED=true
```

## Step 5 · Register the server and host in Settings → Connections

Sign in as the instance owner and open **Settings → Connections**:

1. **Production database server:**
   - **Host:** `127.0.0.1` (or your private PostgreSQL hostname)
   - **Port:** `5434`
   - **Admin credentials:** `wrenly_admin` and the password set in Step 3
   - **CA certificate:** contents of `.local/prod-pg/certs/server.crt`
   - Click **Save & verify** and confirm verified status.
2. **Deployment host (Coolify target):**
   - Select the matching Coolify server (`localhost`)
   - **SSH host:** `127.0.0.1`, **SSH user:** local Linux account with Docker permissions
   - **Ed25519 host key** (`ssh-keyscan -t ed25519 127.0.0.1`) and an authorized private SSH key
   - Click **Save & verify** and confirm verified status.

## Step 6 · Verify end-to-end with an application

1. Open a working database-backed Next.js or Laravel project in Wrenly.
2. Open **Database → Production** and click **Create Production database**. Wait for **Ready**.
3. Create an initial backup when prompted, review the application's migrations, and apply them
   to Production.
4. Confirm in **Database → Production → Browse data** that Production starts empty and contains no
   Development rows.
5. Click **Publish**, wait for deployment verification, open the live application URL, create or
   modify a record, and confirm the persisted row appears in **Database → Production → Browse data**.

## Runtime checks and recovery

- **Automatic runtime checks (`Deployments → Runtime maintenance`):** Disabled by default.
  Enabling **Enable maintenance** on a live deployment periodically verifies the running
  application and database broker containers without resending credentials. You can **Pause**,
  **Stop published app**, **Inspect saved runtime**, or **Revoke permission** at any time.
- **Interrupted rehearsal or network timeout:** Open **Database → Production → Manage resource**
  and select **Resolve rehearsal**, **Resolve Production operation**, or **Check saved action**.
  Wrenly removes stale temporary containers, verifies existing Production tables over TLS, and
  avoids replaying unconfirmed SQL.
- **Database schema version:** Ensure `bun run db:migrate` has been run in `packages/db`
  (migrations `0048+` are required for Production runtime maintenance).
